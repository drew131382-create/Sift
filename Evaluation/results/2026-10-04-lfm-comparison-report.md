# LFM2.5 替换与 Qwen3-0.6B 对照

> 后续状态（2026-10-04）：用户选择继续采用 Qwen。应用默认模型、打包资源与评测默认值已恢复 Qwen3-0.6B；LFM 权重和以下对照结果保留在项目外。本文数据为切回前的实验记录。


日期：2026-10-04。状态：**已完成本地接入、构建和开发回归；LFM 候选不适合日常交付，未更新 iPhone。**

## 实现

- 应用默认模型替换为 `mlx-community/LFM2.5-1.2B-Instruct-4bit`，固定修订 `dee2f8a2786e6648bb644a7ca40652842490034b`；这是纯文本模型，读取 Vision OCR，不直接看图。
- 仅打包一个模型。原 Qwen 权重与替换前源码保存在项目外，Mac 评测通过显式 `--model-profile qwen0.6 --model /path/to/qwen` 加载基线。
- 模型身份、加载校验、去重版本、设置页名称和许可更新。原文关联、直接提取、场景提示词和字段验证源码保持不变；历史卡片、用户修改和失败重试机制保留。
- 所有权重与分词器按固定仓库修订下载，并核对 Git blob/LFS SHA、字节数及本地 SHA-256。构建前和应用加载仍仅验证本地资源，不使用运行时下载或云端兜底。
- 保留 LFM Open License 1.0、固定原模型许可修订 `0f604ada3f766f9f257460c4c9f0b5d6f69d431b` 及转换来源 NOTICE。不能把新模型标为 Apache-2.0。

## 固定样本与方法

159 张来自用户的 `/Users/ivandrew/Desktop/测试截图`。使用此前训练前冻结的逐图助手审核标签：领取 10、日程 11、消费 8、收藏 48、无关 82，共 77 张有用。没有修改预期标签来让新模型通过；截图、标签和源码快照的校验信息保存在项目外。

这批图片已用于开发、训练实验和既有回归，标签尚未经用户逐项确认，数字字段尚未完整标注。因此，本轮是开发对照，不是独立人工准确率验收，也不能证明达到 90%/98% 目标。

两模型在同一台 Mac（Apple M5、16 GB）依次读取全部原图、运行 Vision 和实际 MLX 推理，不使用 OCR 缓存、旧模型结果回放或监督分类器输出。每次输入最多 2048 tokens，输出最多 192 tokens；保持相同 JSON 结构、场景提示词、直接路径与校验规则，使用各自原生分词器和对话模板。

**159/159 张的 OCR 文字、顺序、位置和置信度完全一致。** 新建 OCRBlock 的 UUID 仅作为程序标识，不进入模型提示；比较时只排除这个 UUID。真正的 OCR 内容没有被排除。

主指标：正确四组收录，或正确跳过无关截图。失败不算正确跳过；收录到错误组算错误。额外分别报告收录、漏收和失败，避免“全不收录”造成虚高。

## LFM 失败定位与推理边界

LFM 完整模型路径的 137 次 JSON 都选择 `category=领取通知`、`arrangement=确认`。这不符合“非日程类别 arrangement=无”的语义约束。解析器按异常保留为可重试失败，没有把它们当作无关、生成空卡，或为提高成功率放宽约束。

为排查接入问题，增加 Mac `--inspect-model` 探针，检查原生对话模板、首词 logits 有限性和无 JSON 约束生成。另用模型发布者转换时的 Python `mlx-lm==0.30.2`、本地同一权重、离线设置执行相同三个固定短提示：

- 26／52／54 个输入 token 的计数一致。
- Swift 首词 logits 均为有限值，关键首词及分数与 Python 一致或只有小幅 BF16 数值差异。
- **三个提示的无约束生成文本完全一致**，包括对普通吃饭聊天的错误分类。

这未发现权重文件损坏或明显的 Swift 分词器／前向计算错误。但三个短提示不是全面的运行时等价证明，也不足以确定具体退化原因。能确认的是：**当前固定 LFM 4-bit 版本在 Sift 现有中文提示与受约束输出流程中不适配**。不能把这份结果外推为 LFM 全系列或所有中文任务的准确率。

首轮 5 张强制模型兼容测试为 0/5。一次 30 张中断诊断保留为 `lfm-initial-interrupted.*`，不计入最终成绩。最终使用重新启动后的完整 159 张结果，没有把中断结果拼接成全量测试。

## 数字字段

既有 12 个部分数字锚点，两模型均精确匹配 11/12；Qwen 有 4 个未完整标注的额外数字字段，LFM 有 3 个；禁止值误填均为 0。这些不是完整数字字段金标准，不能报告 98% 数字准确率。

汽车票原文保留 `09月30日周三20:35`，旧锚点只写 `20:35`，按严格原样匹配计错；没有因此改动预期值。LFM 同样保留这些数字主要因为直接路径，不证明它有提取能力。

MLX 峰值只涵盖其分配器，不是整个进程物理内存，更不是 iPhone 内存。实际 iPhone 推理、飞行模式、发热、耗时和进程内存没有在本轮验证。

## 结论

代码和资源已按要求替换为 LFM2.5，保留为开发候选；**当前结果明显差于 Qwen3-0.6B，不建议日常使用或更新 iPhone**。Qwen 本身 67.9% 的开发回归成绩也没有达到可用验收目标。

如果继续研究 LFM，下一步应独立检查受约束解码与中英文提示的适配，先在开发样本验证，再在固定全量标签上重测两个模型。不能通过将失败改成无关、降低字段证据标准或修改预期标签来制造提升。当前 iPhone 和历史卡片未改动。
